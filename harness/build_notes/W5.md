## Decisions
- HF repo id `iamchum/wp-qwen3.6-35b-a3b-wp-judge-v4-gguf` taken from root README.md (lines 4/15/36) and scripts/_pub4_upload.sh.
  Overridable with `WPJUDGE_MODEL_REPO` (entrypoint default).
- Download: `curl -fL -C - --retry 5` into `/models/$FILE.part`, `mv` on success (A2). Rejects WPJUDGE_MODEL_FILE containing `/` or starting `..`.
- llama flags: `-ngl 999 --jinja --chat-template-kwargs '{"enable_thinking": false}' --parallel ${LLAMA_PARALLEL:-4} -c $((P*8192))`
  (per-slot ctx knob `LLAMA_SLOT_CTX`, default 8192 -> 4x8192). No `-ctk/-ctv` at all (small file needs f16 KV). Extra args pass through via `"$@"`.
- The llama service uses the stock image with the entrypoint bind-mounted read-only (`./docker/llama-entrypoint.sh`), so no custom llama image to build.
- Compose passes `WPJUDGE_MODEL_FILE` to both services (binding 7); harness also gets `WPJUDGE_WORKERS=${LLAMA_PARALLEL:-4}` so client concurrency tracks slots, and `WPJUDGE_API_KEY` passthrough (empty = auth off).
- `WPJUDGE_JOBS_DIR=/data/jobs` set in both images (config default `jobs` is relative); jobs volume mounted there.
- allinone HEALTHCHECK probes llama `:8080/health` because the harness API (r3) has no /health endpoint.
- No php-cli anywhere (A1).

## Deviations
- allinone copies the harness source to `/opt/wpjudge/` instead of `/app/` because `/app` in the llama image holds llama-server and its .so files. The `harness` target uses `COPY . /app/` exactly as binding 11 says.
- `.dockerignore` also excludes `*.md` and `docker-compose.yml` (not needed at runtime). pyproject has no `readme` field, so this is safe; if W4/W7 add `readme = "README.md"`, remove `*.md` from .dockerignore.

WPJUDGE_MODEL_FILE=wp-judge-v4-pruned-k224.small-IQ3_XXS-experts.gguf sg docker -c 'docker compose up -d'
