# W3 aggregate — build report

## Files

## API
`build_report(target_meta, model_meta, judgments, skips, cfg, files_scanned=None) -> dict` (schema v1).
- `files_scanned`: explicit arg wins; else `target_meta["files_scanned"]`; else 0. So W4 can pass the
  count from `collect_units` (binding change 7) or have `load_target` put it in target_meta — both work.
- `model_meta` passed through as `{file, base_url}`. `cfg` is `wpjudge.config.Config` (uses cap_dims,
  cap_threshold, cap_value, coverage_threshold).

## Decisions
- overall: LOC-weighted mean over judged units, `round(.., 1)`; weight `max(loc, 1)` (guards loc 0).
- Cap: every (judged unit, cap dim) with JSON score <= cap_threshold -> one `cap_reasons` entry
  `{id, dimension, score}` (a unit low on both dims appears twice). `overall = min(uncapped, cap_value)`.
- Zero judged: overall + uncapped = null, capped false, low_coverage true. Zero units: pct 0.0.
- `pct` rounded to 1 decimal; `low_coverage` uses the rounded pct (`pct < threshold`).
- verdict_counts: judged rows only, always has PASS and FAIL keys (0 default), other verdict strings
  passed through as given.
- dimensions: keys sorted; mean/std rounded 2 dp, low_rate 3 dp; only numeric JSON scores of judged rows.
- rank: r2 §5 verbatim logic on judged rows; prose supplies reason text only, JSON score decides
  polarity (absent key = N/A). Anti-pattern examples are `"file:line name"` (one per topic); patterns
  carry no examples.
- worst_functions: sort by `(overall_score, id)` — id is a string, so "a.php:10:x" < "a.php:1:y".
- functions[]: judgments minus `code`/`raw` (all other keys kept: id, kind, end_line, attempts, error,
  ...), then skip rows in the exact binding-change-4 shape, in input order.
