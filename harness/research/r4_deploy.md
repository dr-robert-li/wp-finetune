# R4 Deploy: aarch64 + CUDA findings

Date 2026-10-10. Host: NVIDIA GB10, compute capability 12.1 (sm_121), driver 580.178.04 (CUDA 13.0), Docker 29.6.2, Compose v5.2.0. Nothing was run in Docker: `rli` is not in the `docker` group.

## 1. Official image: yes, arm64 + CUDA exists

Evidence comes from ghcr.io manifest queries:

| Tag | Platforms | CUDA | arm64 size | Build |
|---|---|---|---|---|
| `server-cuda` (= `server-cuda12`) | linux/amd64, linux/arm64 | 12.8.1 | 2.4 GB | b11515, 2026-10-09 |
| `server-cuda13` | linux/amd64, linux/arm64 | 13.4.1 | 2.4 GB | b11515 |

The pinned tags `server-cuda13-b11515` and `server-cuda-b11515` both return 200. The image config shows `ENTRYPOINT ["/app/llama-server"]`, `LLAMA_ARG_HOST=0.0.0.0`, port 8080, `curl` included (its own HEALTHCHECK uses it) and `NVARCH=sbsa`.

**Use `server-cuda13`, not `server-cuda`.** The reason is in `ggml/src/ggml-cuda/CMakeLists.txt` (local checkout `/home/rli/work/llama.cpp`):
- The default arch list adds `120a-real` for CUDA 12.8 and later, and `121a-real` only for CUDA 12.9 and later. The workflow builds `cuda12` with 12.8.1 (`.github/workflows/docker.yml` lines 90-93), so that image has no sm_121 SASS. `120a` arch-specific code does not run on sm_121, so it falls back to JIT from `90-virtual` PTX. That means a slow first start, a JIT cache that may rebuild on every container start, and no Blackwell-specific paths.
- `server-cuda13` (13.4) includes `121a-real` SASS.
- Driver 580 is CUDA 13.0. A CUDA 13.4 runtime on a 13.0 driver relies on CUDA minor-version compatibility, which is fine for precompiled SASS. The `NVIDIA_REQUIRE_CUDA` string includes `brand=*,driver>=580,driver<581` alternatives (space-separated means OR), so the runtime's requirement check passes. **Not verified on the host. This is the first thing to smoke-test.**

Options (a) building from source and (c) NGC are therefore not needed. Fallback if `server-cuda13` fails on driver 580: build on `nvidia/cuda:13.0.2-devel-ubuntu24.04` (arm64 confirmed on Docker Hub, matches the host CUDA 13.0), running `.devops/cuda.Dockerfile` with `--build-arg CUDA_VERSION=13.0.2 --build-arg CUDA_DOCKER_ARCH=121a-real`. Last resort is option (b): the existing host build `/home/rli/work/llama.cpp/build/bin/llama-server` plus a harness-only container with `WPJUDGE_BASE_URL=http://host.docker.internal:8080/v1` (`extra_hosts: host-gateway`).

## 2. NVIDIA container toolkit: installed

- `nvidia-container-toolkit` 1.20.1, `/usr/bin/nvidia-ctk`, `nvidia-container-runtime` and `-hook` are all present. `/etc/nvidia-container-runtime/config.toml` has `mode = "auto"`.
- A CDI spec exists at `/var/run/cdi/nvidia.yaml`, generated by DGX OS `nv-docker-gpus.service`.
- There is no `/etc/docker/daemon.json`. That is fine: `--gpus` / compose `deploy.devices` uses Docker's built-in nvidia driver, which calls `nvidia-container-runtime-hook`, and Docker 28.2+ also has CDI enabled by default. No `runtime: nvidia` is needed.

The compose stanza:
```yaml
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: all
          capabilities: [gpu]
```
If that errors, the CDI alternative is `devices: ["nvidia.com/gpu=all"]` at service level.

## 3. Harness image + model download

- Base: `python:3.12-slim` is multi-arch, arm64 about 41 MB compressed. Variant A, with PHP, adds `apt-get install --no-install-recommends php-cli` (Debian bookworm PHP 8.2). Tokenizer and json are built in, which is what `scripts/php_extract_functions.php` needs, and it adds about 20 MB. Variant B (pure-Python extractor) drops that line.
- Download: **use curl, not `hf`.** The resolve URL returns `302` to the Xet CDN and then honours `Range` (`HTTP 206`, `content-range: bytes 0-0/16579196960`, `accept-ranges: bytes`). So `curl -fL -C -` resumes, and curl is already in the llama image (0 extra bytes). `pip install huggingface_hub[cli]` adds about 10-30 MB of Python dependencies to an image with no venv. It is resumable too, but it brings nothing extra for one public file. SPEC R3.1 says `hf download`. **I propose amending it to curl**: same behaviour, no token, resumable.
- File sizes (HF tree API): IQ4_XS is 16,579,196,960 B; small-IQ3_XXS is 12,869,398,560 B.

## Recommended shape (one)

**Compose with two services: the official `ghcr.io/ggml-org/llama.cpp:server-cuda13-b11515` running the model, and a slim harness image.** The model download happens in the llama entrypoint, into a named volume. The all-in-one image is a second target `FROM` the same llama image.

### docker-compose.yml (draft)
```yaml
services:
  llama:
    image: ghcr.io/ggml-org/llama.cpp:server-cuda13-b11515
    environment:
      WPJUDGE_MODEL_REPO: iamchum/wp-qwen3.6-35b-a3b-wp-judge-v4-gguf
      WPJUDGE_MODEL_FILE: ${WPJUDGE_MODEL_FILE:-wp-judge-v4-pruned-k224.IQ4_XS.gguf}
      LLAMA_PARALLEL: ${LLAMA_PARALLEL:-4}
      LLAMA_CTX: ${LLAMA_CTX:-32768}
    volumes: [models:/models]
    entrypoint: ["/bin/sh", "-c"]
    command:
      - |
        set -e
        M=/models/$$WPJUDGE_MODEL_FILE
        if [ ! -f "$$M" ]; then
          curl -fL -C - --retry 5 -o "$$M.part" \
            "https://huggingface.co/$$WPJUDGE_MODEL_REPO/resolve/main/$$WPJUDGE_MODEL_FILE"
          mv "$$M.part" "$$M"
        fi
        exec /app/llama-server -m "$$M" -ngl 999 --jinja \
          --chat-template-kwargs '{"enable_thinking": false}' \
          --parallel $$LLAMA_PARALLEL -c $$LLAMA_CTX --host 0.0.0.0 --port 8080
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://localhost:8080/health"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 40m      # first run: 16.6 GB download + ~1 min load
      start_interval: 10s    # polls fast during start, healthy soon after load
    deploy:
      resources:
        reservations:
          devices: [{driver: nvidia, count: all, capabilities: [gpu]}]
    restart: unless-stopped

  harness:
    build: {context: ., dockerfile: harness/Dockerfile, target: harness}
    depends_on:
      llama: {condition: service_healthy}
    environment:
      WPJUDGE_BASE_URL: http://llama:8080/v1
    volumes: [jobs:/data/jobs]
    ports: ["8000:8000"]
    restart: unless-stopped

volumes:
  models:
  jobs:
```
`/health` returns 503 while loading and 200 when ready, and `start_period` failures don't count against `retries`.

### harness/Dockerfile (draft, two targets)
```dockerfile
# --- thin harness (compose) ---
FROM python:3.12-slim AS harness
RUN apt-get update && apt-get install -y --no-install-recommends php-cli \
 && rm -rf /var/lib/apt/lists/*          # variant B: delete this RUN
WORKDIR /app
COPY harness/ /app/harness/
RUN pip install --no-cache-dir /app/harness
EXPOSE 8000
CMD ["wpjudge", "serve", "--host", "0.0.0.0", "--port", "8000"]

# --- all-in-one: llama-server + harness ---
FROM ghcr.io/ggml-org/llama.cpp:server-cuda13-b11515 AS allinone
RUN apt-get update && apt-get install -y --no-install-recommends \
      python3 python3-venv php-cli && rm -rf /var/lib/apt/lists/* \
 && python3 -m venv /opt/venv          # Ubuntu 24.04: PEP 668, needs venv
COPY harness/ /app/harness/
RUN /opt/venv/bin/pip install --no-cache-dir /app/harness
COPY harness/docker/allinone.sh /allinone.sh
ENV PATH=/opt/venv/bin:$PATH WPJUDGE_BASE_URL=http://127.0.0.1:8080/v1
EXPOSE 8000
ENTRYPOINT ["/bin/sh", "/allinone.sh"]
```
`allinone.sh` uses the same download block, starts `llama-server ... &`, polls `curl -fs localhost:8080/health` until it returns 200, then runs `exec wpjudge serve`. Run it with `docker run --gpus all -v models:/models -p 8000:8000`. Ubuntu 24.04 ships Python 3.12 and PHP 8.3. The image is about 2.5 GB without the model. Do not bake in the GGUF (that makes a 19 GB image).

## 5. Small-file caveat

The `small-IQ3_XXS-experts` file must keep the default f16 KV cache. **Never add `-ctk q8_0` / `-ctv q8_0`**: that combination fails the agreement bar (README line 63, CHANGELOG, INVENTORY line 87). The drafts set neither flag. Do not expose them as a configurable option. Keep `max_tokens` 2048 and retry when `<judge_output>` is missing.

## User actions

1. `sudo usermod -aG docker rli`, then log out and back in (or `newgrp docker`). Required for every container test.
2. No toolkit or daemon.json changes are expected. If the GPU stanza fails, run `sudo nvidia-ctk runtime configure --runtime=docker && sudo systemctl restart docker`.
3. First run needs about 17 GB free for the `models` volume, plus 2.4 GB for the image.

## Risks

- **Driver 580 vs a CUDA 13.4 image** has not been run. Smoke test: `docker run --rm --gpus all ghcr.io/ggml-org/llama.cpp:server-cuda13-b11515 --version`, then a 1-token completion. If it fails, use the 13.0.2 source build above.
- **Do not use the `server-cuda` (12.8) tag**: it has no sm_121 SASS (PTX JIT).
- Floating `server-cuda13` tags change daily, so pin `-bNNNNN`. The host server is at 8f114a9b5 (2026-07-10), so b11515 is newer. Re-check the parity of agree_rho and output format, especially `--chat-template-kwargs` and `--jinja` behaviour.
- If the healthcheck `start_period` is shorter than the download, the harness never starts. 40 min assumes ≥ 7 MB/s.
- The CDI spec in `/var/run/cdi` is regenerated by a DGX service. After a driver update, restart Docker if the GPUs vanish.
